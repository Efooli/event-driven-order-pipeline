# Architecture Decision Records

## ADR 1: SQS + SNS fan-out instead of direct Lambda chaining

**Decision:** The Order API pushes to SQS rather than invoking the Order Processor Lambda directly. The Order Processor publishes to an SNS topic rather than calling the Notifier and Inventory Updater Lambdas directly.

**Why:** Direct Lambda-to-Lambda calls create tight coupling — if the Order Processor is down or slow, the Order API's response time degrades or fails outright, even though accepting the order doesn't actually require the processor to run synchronously. SQS decouples that: the API can return a fast "accepted" response the instant the message lands in the queue, and the processor consumes at its own pace.

SNS fan-out solves a different problem: one event (`OrderCreated`) needs to reach two independent consumers (Notifier, Inventory Updater) without the Order Processor needing to know about either of them. Adding a third consumer later means subscribing a new Lambda to the topic — zero changes to the processor itself.

**Trade-off:** Asynchronous processing means the client doesn't get immediate confirmation that their order was fully processed, only that it was accepted. For this use case that's acceptable (order confirmation emails are inherently async anyway), but it wouldn't suit a flow requiring synchronous confirmation (e.g. real-time payment authorization).

## ADR 2: DynamoDB instead of RDS

**Decision:** Order records are stored in DynamoDB rather than a relational database like RDS/PostgreSQL.

**Why:** The access pattern here is simple and known upfront — writes and reads keyed by `orderId`, no complex joins or ad-hoc queries. DynamoDB's on-demand pricing and automatic scaling fit a low, spiky traffic pattern (typical of a portfolio/demo project) far better than provisioning and paying for an always-on RDS instance. It also removes an entire category of operational work — no connection pooling, no VPC networking headaches for Lambda-to-RDS connectivity, no patching.

**Trade-off:** DynamoDB is a poor fit the moment you need multi-table joins, complex ad-hoc reporting queries, or strong relational integrity across entities. At scale, if the system grew to need rich queries across orders, customers, and inventory simultaneously, RDS (or a read-replica/analytics layer alongside DynamoDB) would likely be reintroduced.

## ADR 3: Idempotency strategy

**Decision:** Every incoming order request either supplies a client-generated idempotency key or has one generated by the Order API. The Order Processor performs a conditional write to DynamoDB keyed on that idempotency key — if a record with that key already exists, the write is rejected and the message is treated as a duplicate (logged, not reprocessed).

**Why:** SQS guarantees at-least-once delivery, not exactly-once. That means the same message can legitimately be delivered and processed more than once (e.g. after a Lambda timeout where the function actually completed but didn't report success in time). Without idempotency, a network retry or a Lambda timeout could result in duplicate orders, duplicate inventory decrements, or duplicate confirmation emails — all of which are real user-facing bugs, not edge cases.

**Trade-off:** This adds a conditional-write check on every single order, which is a small latency and complexity cost. It's the right trade for correctness here — silently double-charging or double-shipping an order is a much worse outcome than a few extra milliseconds of processing time.
